设备接入验收后的第一次省调联调，调度自动化处的王工把模拟主站指向我们 EMS 的 IP，点了"连接"。三秒后模拟主站报错：连接超时。我看着屏幕愣住了——OpenEMS 明明有 IEC 104 模块，为什么连不上？

十分钟 后我在源码里找到了答案，也在这个答案里看到了本章要讲的所有东西：规约的角色问题、总召的规矩、AGC 指令进来之后的两级仲裁。这一章是"两个细则"考核的正面战场，也是我们 fork OpenEMS 以来改动最深的协议层。

## 一、事故现场：方向反了

先说联调失败的原因，一句话：**OpenEMS 上游的 IEC 104 模块是"客户端"角色，而省调联调需要我们是"服务端"。**

IEC 60870-5-104 里主站（控制站）和子站（受控站）的角色是明确的：省调是主站，负责发起连接、发总召、下发遥控遥设命令；场站侧是子站，监听端口、响应总召、上报遥测遥信。翻开 OpenEMS 的 `Bridge.Iec104.Tcp` 源码，第一行连接逻辑就是 `new ClientConnectionBuilder(this.ip)`——它主动去连别人，是站在"场站 EMS 去连一台 RTU"的视角写的：从 RTU 读遥测遥信，往 RTU 写控制点。配套的 `Rtu.Iec104` 设备组件也是这个语义：把远动 RTU 当成一台"设备"接进来。

这个设计对欧洲的户用和工商业场景完全够用——FENECON 的系统对接自家网关，客户端足矣。但国内省级调度的现实是：**调度数据必须直接进调度数据网，省调主站要能连到你**。我们要么让 EMS 内置 104 子站能力，要么在场站里加一台传统远动装置做协议转换。前者是把 EMS 升级成"调度级设备"的必经之路，后者多一个盒子、多一套点表、多一层故障点。

决策不纠结：**自研 104 子站模块**。这也延续了 ch04 的路数——上游没做的，恰恰就是我们该做的。

## 二、梳理：104 规约速成与两个模块的分工

动手之前，我把 104 规约里联调要用到的核心概念压缩成一页纸，贴在工位上。这里也给你压缩版，五个点：

**第一，规约是有状态的。** Modbus 是一问一答的"无状态"协议，断了重连接着问就行。104 不是：TCP 连接建立后要依次走"连接建立 → STARTDT 启动数据传输 → 总召唤全量同步 → 周期/突发上送"的流程，任何一步顺序错了，主站直接判死链。状态机做错一步，后面全错。

**第二，四个超时参数撑起可靠性。** t0 是连接建立超时，t1 是发送报文后等确认的超时，t2 是无数据时发确认的超时，t3 是空闲链路的测试帧周期。这些值要跟主站侧配置严格对齐，联调阶段一半的"灵异故障"最后都查到参数不一致上。

**第三，总召唤（总召）是同步基石。** 子站上线后主站先发总召（C_IC_NA_1），子站把全站所有测点的当前值一次性打包上报，之后才转入变化上送——有变化才报，没变化不占带宽。OpenEMS 的客户端桥里就有现成范本：连接成功后立即 `sendGeneralInterrogation()`，断线重连后重发总召。我们把这套逻辑镜像到了子站端。

**第四，报文寻址靠公共地址加信息对象地址。** 公共地址（Common Address）标识场站，IOA（Information Object Address）标识具体测点。省调发的每条 AGC 指令，本质是一个 IOA 上的设点命令（C_SE_NC_1，短浮点值）；我们上报的每个遥测，也是按 IOA 组织的短浮点（M_ME_NC_1）。点表，就是 IOA 和 EMS 内部通道的映射表。

**第五，遥控有"选择-执行"两步确认。** 关键开关量命令（C_SC_NA_1）支持 SBO（Select Before Operate）：先选择、主站回确认、再执行——防止一条误发的报文直接操作设备。这套机制在写代码时容易偷懒跳过，但调度验收时会查。

分工也理清了：上游的 `Bridge.Iec104.Tcp`（客户端）**保留**，作为 B 通道连场站远动 RTU 的转发口，用于对账和后备；我们新增 `io.openems.edge.rtu.iec104.server` 模块（子站端），作为 A 通道直接面对省调。双通道在 ch08 讲 AGC 时还会再出现——调度对可靠性有冗余要求，单通道是过不了验收的。

## 三、底层原理：子站模块怎么长出来

自研子站模块的技术底座还是 j60870——OpenEMS 的客户端桥用的就是它（`org.openmuc.j60870`），这个库同时提供了服务端 API（`ServerConnectionBuilder`），我们等于站在上游验证过的依赖上盖房子，没有引入任何新依赖，bnd 构建链零改动。

模块结构上，我们把上游 `AbstractOpenemsIec104Component` 的"点映射 + 回调"范式整个继承了下来。客户端版的核心数据结构是两个记录类：`TeleValue`（遥测：IOA → 通道地址 + 类型 + 定标）和 `TeleSignal`（遥信：IOA → 通道地址）。子站端我们复用同一套映射，只是数据流向反过来：客户端版是"收到 ASDU → 按 IOA 查映射 → 更新通道"；子站版是"总召到来 → 遍历映射 → 打包 ASDU 回报"，以及"通道值变化 → 按 IOA 打包突发上送"。

具体三个机制值得展开：

**总召响应。** 收到 C_IC_NA_1（激活）后，先回激活确认（ACT_CON），然后遍历全部遥测遥信映射逐点上送，最后回激活结束（ACT_TERM）。漏回 ACT_TERM 是新手最常见的坑——主站会一直等"总召结束"标志，等不到就重发总召，形成总召风暴。我们联调第一天王工模拟主站的日志里就躺着一条"总召未终结"告警，跟连接超时叠在一起，把水搅得更浑。

**变化上送与死区。** 每个控制周期（我们配的 1 秒）扫描一遍映射表，通道值相对上次上送值的变化超过死区才上送（COT=突发或周期）。死区配置不当的后果很现实：死区太小，省调侧被每秒几百条遥测刷屏，通信流量超标；死区太大，AGC 考核用的实发功率数据太粗，精度考核吃亏。功率类测点我们最终定在满量程的 0.1%，这是跟省调自动化处逐条对出来的。

**指令接收与回执。** 收到 C_SE_NC_1 设点命令：回 ACT_CON 确认收到 → 值合法性校验（越限检查）→ 交给 AGC 仲裁层执行 → 回 ACT_TERM 表示执行完毕。校验不通过就回否定确认（ACT_CON 负帧），省调侧会记一条"执行失败"——这比默默吞掉指令诚实得多，调度员看得到，也符合"可控、透明"的验收要求。

顺带一个工程细节：104 的报文里时间是可选的（M_ME_TF_1 带时标、M_ME_NC_1 不带）。省调考核 AGC 响应时间用的是**主站侧的指令下发时刻到实发达标时刻**，所以我们在收到指令和实发达标两个事件上都打了本地毫秒级时标，跟主站时标做对账——联调时还真靠这个抓出过一次 NTP 没配好导致的 8 秒"虚假响应延迟"。

## 四、正确姿势：AGC 两级仲裁

指令能进来了，下一个问题是：省调说"全场目标 180MW"，EMS 怎么变成 64 台风机、700 台组串逆变器对应的功率数值和 24 台 PCS 的充放计划？我们的答案是两级仲裁，每级职责严格分开。

**第一级：调度接口仲裁（子站模块内）。** 这一级只做四件事，全部跟"规约正确性"相关：

1. **远方/就地闸门**：遥信表里有"远方控制允许"位（对应上游 `Rtu.Iec104` 范式里的 REMOTE_CONTROL_ENABLED 点），该位为就地时，所有 AGC 指令回否定确认并记事件。这道闸门是调度规程的硬要求，验收时必查；
2. **越限钳位与校验**：目标功率超出全场可调范围（当前可发上限-下限）的指令，负确认并上送原因；
3. **指令时序**：同一时刻只接受最新指令，旧指令未执行完又被新指令覆盖时，以新为准、旧作废——AGC 是跟踪问题，不是队列问题；
4. **双通道对账**：A 通道（子站直连省调）为主用，B 通道（客户端连 RTU 转发口）只读。两边都收得到指令时做一致性核对，不一致告警但不执行——执行权永远只在主用通道。

仲裁结果是一个统一的内部对象："全场目标功率 + 有效时刻 + 来源通道"，写进一个专用 Channel，向全场广播。

**第二级：场内分配仲裁（周期控制环）。** 每个控制周期拿全场目标，按当前可用设备分解：先扣除不可调设备（故障、通信中断的），光伏和风电按可用容量比例跟随，储能拿走偏差量（同时受 SOC 和充放电约束保护）。这套分配逻辑的完整设计——尤其是储能"接住偏差"的边界条件——是 ch08 的主题，本章只强调一句：**第一级仲裁绝不做功率分配，第二级仲裁绝不直接碰规约**。职责混了，排查问题时就是灾难：你分不清一条没执行的指令是"没收到"还是"收到了没分对"。

## 五、数据说话：联调三周的账

子站模块开发加联调的量化盘点：

- **点表规模**：104 上送总计 214 点——遥测 152 点（全场及各子系统有功/无功/电压/电流/频率/SOC）、遥信 62 点（开关状态、故障、远方就位等）。全部经 OSGi 配置化（IOA、定标、偏移都是配置项），点表变更零代码改动——跟调度对点表的三轮变更，每次都是改配置热加载，没用过一次重启；
- **指令链路时延**：模拟主站实测，指令从主站发出到子站回 ACT_CON，P99 为 43 毫秒（网络 2ms 内 + 解析校验 5ms 内 + 仲裁入队 1ms 内）；全场实发功率跟踪到目标值 95% 的端到端时间，均值 38 秒——这个值由设备爬坡率决定，EMS 自身只贡献了其中不到 1 秒；
- **总召同步**：214 点全量总召回报耗时 1.8 秒；断线重连后自动补总召，链路恢复到数据重新同步完毕实测 7 秒以内（含 5 秒重连间隔）；
- **SBO 用例**：遥控类联调用例 18 个全部通过，包括"选择后超时不执行""选择后主站取消"这类边界；
- **零新增依赖**：子站模块约 2100 行（含测试），构建链未动——j60870 同时覆盖客户端和服务端，是当初选它而非自己撸规约的关键原因。

第三周验收会上的最后一个测试项目是"拔网线"：联调中物理断网 30 秒再恢复，子站自动重连、自动补总召、期间指令缓存与丢弃策略符合约定。王工在验收单上签了字，补了一句："你们这个子站，比不少老 RTU 的重连行为干净。"

## 六、面试怎么答

"讲讲你对接调度规约的经验，104 和 Modbus 有什么本质区别？"答题框架：

1. **先讲状态**：Modbus 无状态、104 有状态——连接流程、总召同步、变化上送、确认重传，一句话点透；
2. **再讲角色**：主站/子站的职责边界，以及"客户端模块不等于能当子站"——用我们自研子站模块的例子说明协议库选型（j60870 双端覆盖）和角色适配是两件事；
3. **落细节**：主动讲总召风暴（漏回 ACT_TERM）或时标对账（NTP 坑）这类一手细节；
4. **收在架构**：规约层与业务层分离——第一级仲裁只管规约正确性，第二级只管功率分配，接口是一个统一的指令对象。

如果追问"怎么保证调度指令不被误执行"，把远方/就地闸门、越限负确认、SBO 三道防线讲清楚，再补一句双通道对账不执行只告警的设计取舍。

## 七、落地清单

1. 接入调度前先分清角色：主站发起、子站响应，"有客户端模块"不等于"能当子站"，选协议库时看双端覆盖；
2. 104 状态机的每个确认帧都不能省：ACT_CON、ACT_TERM 漏一个就是总召风暴，联调日志第一页永远是它们；
3. 点表必须配置化：IOA、定标、偏移全部进配置，对点表阶段的变更要以"热加载"为验收标准；
4. AGC 指令链路两端打时标，NTP 是联调第一天就该验证的基础设施，不是"到时候再看"；
5. 下一章（ch06），我们进入全系列技术含量最高的部分：把上游基于遗传算法的调度引擎（energy 优化器）剥开——它每 15 分钟在算什么、怎么算，以及为什么我们必须把它移植成"甘肃模式"。
