等保测评的第 3 天，测评师小林指着我们的网络拓扑图问了一个问题："你们的管理后台跑在哪台机器上？"我回答"EMS 服务器上"。他放下笔说："那你们这套系统现在生产控制大区里有 Web 服务，这份拓扑过不了。"

这句话让项目停了一周。我们fork 的 OpenEMS 有一套完整的 Backend（后端数据聚合、UI、用户管理），部署时天然是"一体化"的——但在国内，这套部署方式撞上了《电力监控系统安全防护规定》（14 号令）的红线：生产控制大区和管理信息大区必须物理隔离，控制大区里不能有面向管理人员的 Web 应用。这一章讲那堵墙怎么砌、门怎么开——安全分区不是部署细节，它反过来重塑了整个系统的边界。

## 一、事故现场：一张过不了测评的拓扑图

先把问题摆清楚。14 号令把电力监控系统划成四个区：生产控制大区（安全 I 区：实时控制，如机组/场站监控；安全 II 区：非控制生产业务，如功率预测）和管理信息大区（安全 III 区：生产管理；IV 区：管理信息），大区之间要求隔离——控制大区到管理大区**禁止通用网络服务直连**（尤其 HTTP/Web 服务），必须经电力专用横向隔离装置；管理大区往控制大区的反向传输，要经隔离装置严格限制。落到我们项目上，三条硬约束：

1. **EMS 的实时控制部分（Modbus 下达、IEC 104 上省调、秒级 AGC 环）必须住 I 区**——这是它的天职；
2. **功率预测类业务按惯例可住 II 区**——它与控制相关但非实时控制；
3. **我们的管理后台（Web UI、用户权限、报表）、历史数据 API 是典型的管理大区业务**，绝不能出现在 I 区。

而 OpenEMS 的原生部署形态恰好踩了第 3 条：Edge 与 Backend 通过 WebSocket 通信，Backend 一体承载 UI、数据、鉴权——部署图上一画，"控制大区里有 Web 服务"，直接判死。

复盘那一周的结论很清晰：这不是运维问题，是架构问题。分区方案必须在软件架构上有对应的切割线——**代码里如果没有一条干净的边界，墙上砌得再厚，业务流量也会把墙打穿**。

## 二、梳理：把 OpenEMS 的通信面翻个底朝天

切割之前，先盘点 Edge/Backend 之间到底有哪些通信，一根一根处理。我们列了五类：

**遥测与事件上行（Edge → Backend）。** Edge 层的 TimedataProvider 接口把通道数据源源不断送 Backend 存储。数据量大、频次高，但**方向单一、内容只读**——这是最容易安全处理的一类。

**RPC 与 UI 交互（双向）。** Backend 的 UI 通过 JSON-RPC 调 Edge 的方法（改配置、读诊断、下指令的入口之一），Edge 也主动向 Backend 推状态。这是最危险的一类：**它同时具备"管理大区用户发起"和"抵达控制大区执行"两个属性**，直连就是从 III 区伸手进 I 区。

**配置下发（Backend → Edge）。** 组件配置变更的通道，同样是"管理动作抵达控制区"。

**元数据同步（双向低频）。** 组件注册、边缘设备发现。

**时间序列查询（Backend 内部）。** UI 看历史曲线，数据在 Backend 存储里，不触达 Edge——这部分只要整个 Backend 搬去 III 区，天然合规。

盘完的结论：真正的难点只有一条——**JSON-RPC 的双向管理通道**。其余要么单向上行（可以做成"推过墙"），要么本来就该住在管理大区。

## 三、底层原理：隔离装置与"单向数据桥"

国内电力监控系统的标准解法是**正向横向隔离装置**：一个专用的硬件盒子，只允许从 I/II 区向 III 区**单向**传输数据，且传输的内容是"纯数据"（透传的通常是被削去网络特征的签约数据流），反向物理断开。它不是防火墙——防火墙是"检查后放行"，隔离装置是"物理上只进不出"。

我们的最终架构顺着这个逻辑定型：

**I 区：Edge 内核 + 控制栈。** 全部 Modbus/104 协议栈、秒级 AGC 环、两级仲裁——ch04 到 ch08 的所有实时逻辑，整体住在 I 区的服务器上。这一区唯一对外的"吐出"是遥测数据流。

**II 区：功率预测模块。** 预测家族（NWP 接入、LSTM 训练、画像聚类）独立成套，与 I 区 Edge 之间经防火墙交换预测结果和少量实测数据（II 区到 I 区是"反向"，经防火墙点对点白名单，只允许预测结果这一个数据流的固定端口）。NWP 的互联网接入在 II 区侧解决——这也是把气象数据引进来的合规路径：**互联网永远不碰 I 区**。

**III 区：Backend 全家 + 管理后台。** OpenEMS Backend、UI、用户管理、历史数据 API、报表——整体搬到管理大区。业主运行人员日常看曲线、改报表，全在 III 区完成，与控制设备之间隔着一堵物理墙。

那 JSON-RPC 管理通道怎么办？答案是**改造成"数据桥"**：I 区 Edge 起一个只读的镜像数据端点，把管理界面需要的运行数据（通道实时值、组件状态、诊断信息）经正向隔离装置**单向推**到 III 区的 Backend；III 区的"操作类请求"（改配置、启停组件）则走**人工流程**——管理大区出工单，运维人员通过堡垒机登录 I 区的本机管理终端执行。web 界面上那个"远程启停组件"按钮，从此在管理大区的页面上消失。

这个取舍在项目里争论过。有人提议用隔离装置的"反向文件摆渡"功能把操作指令递进去——测评口径下技术上可行，但每个反向摆渡都是一次审计负担，且操作时效差。最后的决定朴素而坚定：**控制操作的时效性要求（秒级）与管理操作的便利性（随时点按钮）本来就不同频，硬要打通就是把低安全的便利性灌进高安全的实时区**。真正需要秒级反应的操作，本来就在 I 区的自动控制环里；需要人工判断的操作，晚十分钟执行通常不致命。

## 四、正确姿势：让架构长出这条边界

墙上的一次性改造不难，难的是让代码从此守住这条线。我们落了三条工程纪律：

**第一，通信面收敛为一个模块。** I 区里新建了一个"数据出口"模块，全场唯一被授权把数据送出控制大区的组件——所有外送数据（I 区到 II 区的实测样本、I 区到 III 区的镜像遥测）都从它手里走。它有独立的白名单配置（目的地、端口、数据类别），CI 里加了一条扫描规则：**任何其他模块出现对外网络地址，构建直接红灯**。这条机器规则的价值在半年后才显现：一个新同事给协议模块里顺手加了个"上传诊断日志到 FTP"的便利功能，CI 红灯把他拦在代码评审之前——墙不需要人人记得，CI 替你记。

**第二，I 区的零依赖审计。** I 区的 Edge 镜像做了一次依赖大扫除：所有与 UI 相关的 bundle、所有带 Web 服务器的组件（包括 OpenEMS Backend 的 UI 依赖），从 I 区发行包里整体剥离。CI 的第四道关（ch03 的冒烟拓扑）相应升级：I 区冒烟拓扑增加了"端口扫描断言"——发行包启动后，除协议端口和数据出口端口外，任何监听端口都是失败。**合规从"部署时的布置"变成"构建时的断言"**。

**第三，审计日志的跨区镜像。** I 区的所有控制操作（无论来自自动环还是堡垒机人工操作）写本地审计日志，并随遥测数据流经隔离装置单向镜像到 III 区归档——审计人员不需要进控制大区就能查完整操作史。这个设计后来在测评时被小林特别圈了好评："多数项目把审计日志锁在控制区里，查一次要办一次进区手续。"

## 五、数据说话：分区改造的账

一周停工换来的改造，量化盘点：

- **架构切割**：五类通信面里 4 类直接归位（上行数据流改单向推送、历史查询随 Backend 搬 III 区、元数据同步停用、II 区独立），1 类（JSON-RPC 管理）改造为"只读数据桥 + 堡垒机人工流程"；
- **I 区发行包瘦身**：剥离 UI 与 Web 相关 bundle 共 37 个，I 区镜像体积减 31%——副产品是攻击面收缩：I 区对外暴露的监听端口从 7 个降到 3 个（Modbus 从站侧、104 子站、数据出口）；
- **数据桥开销**：镜像遥测经隔离装置的传输延迟实测小于 200 毫秒，对管理侧"看曲线"场景无感；控制大区侧的资源占用增加不足 2%；
- **测评结果**：整改后一次过审，拓扑、访问控制、审计三条线均无整改意见。项目停一周换"零整改意见"，这笔账在业主那边被记成了正面案例；
- **损失的便利**：管理大区页面的"远程启停"按钮下线，组件启停平均响应时长从"即时"变成"约 15 分钟"（工单+堡垒机流程）。投运半年统计，真正需要人工启停组件的次数：月均 1.3 次——便利性的损失，远比想象中小。

那 1.3 次/月的数字最后成了争论的终结者：**当一个"安全代价"对应的实际使用频率是月均 1.3 次时，为它保留一条穿越隔离墙的通道，就是在为一个低频便利支付高频风险**。

## 六、面试怎么答

"电力监控系统怎么做安全分区？你们实际怎么落地的？"答题框架：

1. **先讲规则**：14 号令的大区分界（I/II 控制大区、III/IV 管理大区）、横向隔离的单向性、互联网永不进控制大区——展示你懂"为什么"，不只是"是什么"；
2. **再讲落法**：通信面盘点→分类处理（归位/单向化/人工流程化），强调"软件架构里必须有一条对应的干净边界"，举 CI 端口断言和出口模块白名单两个机制；
3. **答取舍**：主动讲"远程启停按钮下线"的决策逻辑——低频便利 vs 高频风险，用月均 1.3 次的数据收尾；
4. **收一句认知**：安全分区不是给部署图打补丁，是让系统的信任边界显式化——架构里长不出这条线的系统，墙砌得再厚也是漏的。

若追问"隔离装置和防火墙的区别"，一句话：防火墙是"检查后放行"（逻辑隔离），隔离装置是"物理只进不出"（物理隔离）——安全等级差一个数量级，适用边界由 14 号令规定，不是自由选择。

## 七、落地清单

1. 分区改造从通信面盘点开始：把跨区通信一根一根列出来，逐条归位（搬走/单向化/人工化）——盘点不全，墙上必留暗门；
2. 控制大区给"数据出口"收敛成一个模块加白名单，CI 红灯代替人肉记忆——边界要长在构建流水线里，不长在人的自觉里；
3. I 区发行包做零依赖审计加端口断言：部署合规要从构建期就断言，不能等测评期再发现；
4. 控制操作的审计日志单向镜像到管理大区：安全与审计共用一堵墙，审计不必进墙；
5. 下一章（ch11），数据本身成为主角：全场约 6 万个测点、秒级上万个、日均 13 亿个点——这些数据往哪放、怎么压、怎么查，IoTDB 的高频写入和 I 区到 III 区的数据流，是时间序列存储的实战课。
